# Design contract

Witness Memory is an in-process library. It owns local record persistence and evidence selection; the host owns authentication, tool permissions, model consent, retention and delivery.

## Records and revisions

Direct construction and `Record.create` validate metadata before normalization. Audience containers may be lists, tuples, sets or frozensets; source containers must be lists or tuples. Strings, bytes, generators and `None` are not accepted as these containers. Valid containers become immutable tuples. `Record.from_dict` accepts a mapping and normalizes legacy boolean confidence and timestamp values to numeric 0/1 before validation; reading does not rewrite stored payloads. New records still reject bool in numeric fields. Finite int/float subclasses are accepted; confidence remains within [0, 1]. This targeted compatibility path is not a general migration of arbitrary legacy payloads: other invalid metadata still causes an explicit read failure. Deserialization failures in `Store.get` (including historical revisions) and `Store.snapshot` raise `ValueError` identifying the database record ID and a recognized field name, or `payload` for unclassified failures, without forwarding rejected values, memory text or the original exception traceback. Corrupt rows are neither skipped nor rewritten. Empty audience remains private; wildcard audience must stand alone. Source references retain exact positive integer revisions. Optional timestamps may remain `None`. Validation errors identify fields without echoing memory text or rejected values.

Public traversal, recall, consolidation and search-index limits, context budgets and context measurement results require integers, not bool or fractional values, with their documented lower bounds. Search-index limits remain within [0, 10000]. Invalid context budgets are rejected before invoking the measurement callback; its output is validated after invocation. Link weights must be finite numbers in (0, 1], not bool; fractional weights remain supported. Explicit `now` values must be finite numbers, not bool. `Store.put` permits expected revision zero for new records; explicit historical revisions in `Store.get` must be positive integers. Storage argument checks run before storage operations. Exact source references, CAS/history and transactional rollback are unchanged; the SQLite schema version is unchanged. Compatibility is limited to the explicitly documented input forms and legacy normalization above, not every value accepted by earlier releases.

A `Record` separates text, source, explicit author, source trust, audience, namespace, kind, confidence, capture time (`created_at`), optional event time (`occurred_at`), expiry and lifecycle. Unknown author/event time remain `None`. `created_at` is observed capture time, not inferred event time. Timestamps are epoch seconds. Trust defaults to `unknown`, audience to empty/private, and status to active.

Primary `Record.create` IDs retain the existing SHA-256 identity over a JSON tuple of namespace, source, caller anchor and the **entire** text. In 0.2.0, newly created derived records use versioned structured JSON containing namespace, source, caller anchor, full text and sorted unique exact (parent ID, revision) pairs. This applies both to `derive` and to direct `Record.create(derived=True, sources=...)`. Parent order and repeated identical references do not change identity; different parent sets, parent revisions, anchors or text suffixes do. Explicit caller anchors remain part of identity rather than being replaced by provenance.

Persisted IDs and SourceRefs are not recomputed or rewritten when reading existing databases. Legacy derived records remain readable with their original identities and references; recreating a candidate under 0.2.0 can produce a new ID. Identical creation inputs produce an identical ID, not an automatic upsert: inserting an already persisted ID with expected revision zero still raises `ConflictError`. The namespace and ID are the persistence key. Updating text through `dataclasses.replace` retains identity and creates another revision; creating a fresh record from new text creates a different identity.

`Store.put` compares the expected revision inside `BEGIN IMMEDIATE`. New records expect zero. The default expected revision is `record.revision`. A mismatch raises `ConflictError`; it is never silently merged. Each successful write updates the current row and appends its immutable historical revision in the same SQLite transaction. Independent connections use SQLite's locking with a five-second busy timeout by default. Hosts can configure `Store(path, timeout=...)` and `SearchIndex(path, timeout=...)` in seconds; zero means fail immediately on contention. Busy timeout errors propagate without losing already committed records. The concurrent-write test uses a 30-second deadline to accommodate slow hosted Windows disks. Operational and corruption errors propagate.

The database schema version is 1. Unknown schema versions fail explicitly. There is no automatic schema migration or agent-specific backup importer. An ingestion batch and a maintenance run consist of individual atomic record writes; failures can leave earlier successful writes in place.

## Evidence and permissions

`derive` requires persisted parents in one namespace. It creates an unpersisted record, retaining exact parent revisions and intersecting audience permissions. Trust follows the least trusted source: `untrusted` dominates `unknown`, which dominates `trusted`. Confidence never exceeds the least confident parent.

Before recall, `resolve_evidence` walks the complete provenance closure. It detects missing sources, changed revisions, namespace crossings, inactive/expired or incomplete sources, cycles and traversal limits. A derived record with no sources is incomplete. Incomplete evidence is withheld, with no permissive audience fallback. Every ancestor participates in permission intersection; a summary cannot grant access unavailable at its sources.

In version 0.1.2, `max_nodes` counts unique visited records, including the root. Reaching an already visited ancestor does not consume another node; a graph with exactly the allowed number of nodes can pass. Root depth is zero, and `max_depth` is the maximum permitted number of source edges on any path. A longer path to a shared ancestor must still be checked, regardless of parent order. Exceeding either budget produces incomplete evidence with the `limit` issue. Cycles, namespace crossings and revision mismatches remain invalid; traversal bounds never grant access. Repeated traversal is bounded by (max_depth + 1) × the number of edges and can be noticeably slower on dense graphs; optimization is deferred, with no speedup promised.

The intersection has two special cases: `('*',)` is unrestricted, and `()` is private/denied. Concrete audience identifiers are supplied by trusted host code; using the literal `'*'` as a principal is rejected. Mixed wildcard audiences are rejected. An empty audience does not mean “only this agent”: specify that agent's principal explicitly.

Storage and low-level index methods are privileged and do not authorize reads. Retrieval diagnostics include aggregate counts of withheld records in the selected namespace, so do not expose them as a cross-tenant endpoint. Authorized revision receipts omit unauthorized record IDs. Treat every namespace and principal argument as authenticated host context, never as authority claimed inside source text.

A recall is a snapshot, not a delivery authorization lease. Concurrent changes after selection require host revalidation before delivery. Graph and record reads are separate snapshots; revision mismatch withholds edges conservatively. The library does not promise serializable read-plus-delivery across external authorization systems.

## Ranking clock

Direct calls to `agent_memory.retrieval.rank` validate `now` as a finite number before arithmetic. Bool, NaN, infinities, `None` and strings are rejected. Finite negative epoch times, zero, integers and floats remain valid. The ranking formula and its zero-age clamp are unchanged.

## Retrieval

Base recall uses the lexical term matcher and query-centered excerpt logic extracted from an agent runtime. Stop words and a small transliteration table cover Russian and English. Russian inflection uses a prefix heuristic; Latin identifiers remain literal. Dotted versions are kept whole. One or two query terms require all matches; longer queries require at least half, never fewer than two. All-stopword queries return no hits.

Ranking combines lexical overlap, exponential confidence decay and hyperbolic recency. Decay periods are **e-folding time constants**, not half-lives. Confidence is a heuristic ranking value, not a calibrated probability of truth. The current implementation scans the selected namespace in memory; it is not designed or benchmarked for very large stores.

`SearchIndex` is an optional, disposable FTS5 projection with BM25 ordering. It uses Unicode tokenization and quoted literal OR terms. `rebuild` replaces one namespace's projection atomically. Index hits are intersected with authorized canonical records and exact revisions before inclusion. FTS contributes a small reciprocal-rank increment (`1 / (60 + rank)`) alongside lexical candidates. A stale index may miss FTS-only candidates; lexical matching still scans current canonical rows. FTS errors propagate. No vector retrieval or semantic similarity is implemented.

Graph links bind a subject/relation/target to a current record revision. Recall traverses eligible links in both directions, with configurable depth (0–8), per-node fanout and visited-node limits. Path weights decay by 0.6 per depth. A graph relationship is an explicit host assertion backed by a record, not an independently verified logical implication. Updates leave old edges physically present but exclude them until relinked at the new revision.

## Context and models

`context` renders whole JSON evidence blocks with IDs, revisions, sources, authors, trust and primary witness IDs. The default counter is Unicode character length. A caller can supply a tokenizer; its counter must return a non-negative integer. The complete serialized envelope is measured after each candidate block. Oversized blocks are omitted, not clipped. If even the empty envelope does not fit, the result is empty with all hits omitted.

The result reports included/omitted IDs and budget usage. The caller reserves space for the remaining prompt and interprets these receipts. Excerpts may omit context; recovered passages contain offsets and an omission marker. Metadata is not regex-redacted automatically. JSON escaping protects structure, not the model's behavior.

The `Source` and `Model` protocols impose no provider dependencies. `ingest` explicitly consumes source records. `summarize` freezes the supplied parents before the callback and checks them against one namespace snapshot. Parents must be current persisted records in one namespace with complete, active, unexpired provenance under the supplied `now`, `max_nodes` and `max_depth`. Preflight also validates a prospective summary root against that snapshot and those budgets: the additional node, additional depth and combined ancestry must fit before the model is invoked. These provenance and argument checks fail before the callback; model-output validation necessarily happens after the callback and cannot prevent its cost. Unknown or untrusted evidence is not upgraded to trusted evidence; the host remains responsible for authorizing disclosure to its model.

After preflight, `summarize` invokes the supplied model once without holding the Store write lock. It validates that the result is a `ModelOutput` with non-empty string text, optional non-negative integer token counts and optional finite non-negative cost; bool is not a numeric value. Validation errors name fields without including generated text. Missing token counts or cost remain `None`. Duck-typed output objects are not accepted in place of `ModelOutput`; cost accepts finite int/float values (including subclasses), not `Decimal`. These output restrictions are checked after the model call, so rejection does not imply that no provider cost was incurred. The candidate uses the frozen parents and their exact revisions, not a caller-mutated list or refreshed records. It is never persisted automatically. A concurrent source update may therefore make it ineligible on later provenance validation; preflight is not a lease on future source validity. The host must cap spending, handle provider errors, revalidate when necessary and decide whether to persist a candidate.

## Maintenance

`maintain` inspects expired active records; dry run is the default. In 0.2.0, `type(dry_run) is bool` is required: any other value raises `ValueError` before reading a snapshot or writing records. `True` preserves inspection-only behavior; `False` retires each candidate through revision-checked writes. A conflict raises an error. Retirement and history retention are not physical erasure.

`propose_consolidation` adapts deterministic same-kind greedy Jaccard clustering (threshold 0.7). It considers complete, trusted, derived records, partitions them by effective audience, and returns unpersisted source-bound proposals. Primary speech and already consolidated records are excluded. At most 500 eligible candidates are processed by default; exceeding the cap raises rather than silently truncating. The algorithm can mistake negated sentences for duplicates. Host review is required; no source is automatically removed or retired, and confidence is not increased.

Version 0.1.2 checks each prospective proposal with `resolve_evidence` against the same namespace snapshot, clock and `max_nodes`/`max_depth` budgets used for its parents, without SQL writes. Valid parents alone do not guarantee a valid proposal: the new root adds a node and a provenance level. The default return remains a tuple of ready `Record` candidates. Opting into `with_receipt=True` returns a public `ConsolidationReceipt` containing `proposals` and `skipped`. Each `SkippedProposal` identifies exact parent references, a reason and resolver issues, not source text. A candidate exceeding traversal budgets is skipped with reason `provenance_limit`; other incomplete candidate evidence uses `provenance_invalid`. This receipt describes prospective candidates rejected after clustering, not every input excluded by eligibility filtering. Neither return mode persists candidates, retires sources or invokes a provider.

`classify_kind` is a small rule-based classifier, not a semantic extractor. `redact_secret_like` is an optional regex helper for known secret shapes, not a privacy guarantee. Apply a host-specific capture policy if raw secrets must never be stored; applying this helper after persistence does not remove historical data.

## Feedback

`Store.feedback` implements revision-bound feedback. Each command contains a record ID, expected integer revision, namespace, operation ID and outcome. Duplicate detection precedes lifecycle, capacity and CAS checks. Replaying the same command returns its original receipt with `duplicate=True`, including after restart or retirement; reusing its operation ID for a different command raises `ConflictError`. Historical receipts retain their original revision, even when an older release bumped the record revision for an observation. Replay does not renumber receipts or reverse earlier invalidation.

Outcomes are `helpful`, `irrelevant`, `incorrect` and `retract`. In 0.2.0, helpful/irrelevant write only the feedback ledger and return the observed evidence revision. They do not change the record, history, confidence, descendants, FTS projection or graph links. Incorrect/retract retire the record through a new lifecycle revision; that revision and its receipt commit atomically, conservatively invalidating descendants and projection entries bound to the older revision.

The per-record limit is 64 nonterminal (helpful/irrelevant) receipts. A 65th new observation fails without mutation; terminal incorrect/retract remain available at capacity, subject to the existing revision and lifecycle checks. Old receipts and idempotency keys are never deleted. A feedback(namespace, record_id) index supports the lookup. Feedback remains a privileged host write and does not turn an answer-level outcome into a verdict about every retrieved memory. Correction uses a normal revision-checked `Store.put`; automatic supersession is not implemented.

New database files are created with owner-only permissions on POSIX systems. Existing file permissions are not changed. Filesystem policy, backups and encryption remain host responsibilities.

## Existing stores

`CanonicalReadAdapter` works with host callbacks for latest canonical rows, metadata projection, revision identity, eligibility and exact-revision authorization. It materializes the snapshot to detect duplicate IDs before returning data. Unknown scopes deny. Callback errors propagate. Returned values are deep copies. Callbacks are trusted integration code, not instructions supplied by memory text.

This adapter does not fold an append log, authenticate the supplied audience, add missing provenance or lock an external store. Its input must be an already folded, consistent latest-revision snapshot. It is a useful seam for an existing store; it is not a storage migration by itself.

## Release 0.1.3 scope

Version 0.1.3 keeps the 0.1.2 integrity contract and narrows its compatibility impact. Legacy serialized boolean confidence and timestamp values are normalized to numeric 0/1 on read without rewriting stored payloads, while new records still reject bool in numeric fields. Finite int/float subclasses, mapping input to `Record.from_dict` and set/frozenset audiences are accepted. `summarize` also validates the prospective summary root against the same snapshot and traversal budgets before invoking the model. Link weights, search-index limits and context budgets use the shared numeric validators. Deserialization failures in `Store.get` and `Store.snapshot` name the stored record ID and field without forwarding rejected values. Duck-typed model outputs, `Decimal` cost and the previously tightened revision, excerpt and consolidation bounds remain rejected; traversal speed on dense graphs is unchanged.

## Release 0.1.2 scope

Version 0.1.2 strengthens metadata validation, source-revision binding and evidence traversal integrity. It does not change feedback semantics, derivation identity, excerpt selection or graph ranking. These changes are a bounded integrity update, not a claim that every memory failure mode is resolved.

A host can integrate the canonical read adapter without adopting the library's storage, write or consolidation APIs. Such integration is not a global installation or a migration of existing memory and revisions. Passing synthetic library tests does not establish improved live memory or answer quality.

## Supported surface

Python 3.11+ and standard-library SQLite. Optional indexing requires FTS5 in the Python SQLite build. The core has no framework, model, network or environment-variable dependency and performs no work merely by import. Windows, macOS and Linux are CI targets. Coding and research integrations use synthetic sources; real framework certification, scale benchmarks, encryption, embedding providers, physical erasure and a lossless legacy migration are outside 0.1.2.
